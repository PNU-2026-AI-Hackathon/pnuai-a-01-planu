# PlaNU LLM Prompt Improvement Skill

## 목적

사용자가 입력한 자연어 수강 조건을 PlaNU의 구조화 데이터로 정확히 변환하는지 평가하고,
실패 원인을 분석한 뒤 필요한 경우에만 프롬프트를 개선한다.

이 스킬의 핵심 반복 과정은 다음과 같다.

1. LLM 평가 테스트 실행
2. 실패 사례 분류
3. 실패 원인 판단
4. 프롬프트 수정
5. 전체 회귀 테스트 재실행
6. 변경 전후 결과 보고

테스트를 통과시키기 위해 평가 데이터나 기대값을 임의로 변경해서는 안 된다.

---

## 평가 대상

주요 구조화 필드는 다음과 같다.

- `required_course_names`
  - 반드시 포함해야 하는 과목
- `preferred_course_names`
  - 가능하면 포함하고 싶은 과목
- `excluded_course_names`
  - 절대 포함하면 안 되는 과목
- `disliked_course_names`
  - 가능하면 피하고 싶은 과목
- `preferred_elective_areas`
  - 선호하는 교양 영역
- `earliest_start_time`
  - 허용 가능한 가장 이른 수업 시작 시각

프로젝트의 실제 스키마가 위 이름과 다르면,
테스트를 작성하기 전에 현재 Pydantic 모델과 프롬프트 정의를 확인하고
필드 이름만 실제 코드에 맞게 조정한다.

필드의 의미와 조건 강도는 변경하지 않는다.

---

## 조건 강도 분류 원칙

### 필수 과목

다음 의미는 `required_course_names`로 분류한다.

- 반드시 들어야 한다
- 꼭 포함해야 한다
- 무조건 넣어야 한다
- 이 과목이 없는 시간표는 싫다

### 선호 과목

다음 의미는 `preferred_course_names`로 분류한다.

- 가능하면 듣고 싶다
- 우선적으로 넣어 달라
- 되도록 포함해 달라
- 꼭 필요한 것은 아니지만 듣고 싶다

선호 표현을 필수 조건으로 강화해서는 안 된다.

### 제외 과목

다음 의미는 `excluded_course_names`로 분류한다.

- 절대 듣기 싫다
- 무조건 제외해 달라
- 포함하지 말아 달라
- 이 과목이 있으면 안 된다

### 비선호 과목

다음 의미는 `disliked_course_names`로 분류한다.

- 가능하면 피하고 싶다
- 다른 선택지가 있다면 빼고 싶다
- 우선순위를 낮춰 달라
- 별로 선호하지 않는다

비선호 표현을 완전 제외 조건으로 강화해서는 안 된다.

### 선호 교양 영역

다음 의미는 `preferred_elective_areas`로 분류한다.

- 4영역을 선호한다
- 4영역을 우선 추천해 달라
- 가능하면 4영역에서 골라 달라

영역을 선호한다는 표현을 해당 영역만 허용하는 필수 제약으로 바꾸지 않는다.

### 가장 이른 시작 시각

다음 의미는 `earliest_start_time`으로 변환한다.

- 오전 10시 이후 수업
- 10시보다 이른 수업은 싫다
- 첫 수업은 10시부터 가능하다

동일한 의미를 표현하는 별도 Boolean 필드와 중복 저장하지 않는다.
프로젝트에 `no_morning_classes`, `morning_end_time` 같은 이전 필드가 남아 있다면
현재 스키마의 단일 기준 필드를 먼저 확인한다.

## 작업 절차

### 1. 현재 구현 확인

다음 항목을 먼저 확인한다.

- 자연어 입력을 구조화하는 함수
- LLM 프롬프트 파일
- Pydantic 출력 모델
- 후처리 및 정규화 함수
- 기존 pytest 테스트
- 실제 LLM 호출 여부와 테스트 마커

코드 위치를 추측해서 새 파일을 만들지 말고,
현재 저장소 구조를 확인한 뒤 기존 구조를 따른다.

### 2. 기본 테스트 실행

먼저 실제 LLM을 호출하지 않는 테스트를 실행한다.

```bash
pytest -m "not llm_eval"
```

프로젝트에 다른 마커 이름이 있다면 기존 설정을 따른다.

### 3. LLM 평가 테스트 실행

사용자가 LLM 평가 또는 프롬프트 개선을 요청한 경우에만 실행한다.

```bash
pytest -m llm_eval
```

API 키가 없거나 네트워크 문제로 호출할 수 없으면
프롬프트를 수정하지 말고 실행 불가 원인을 보고한다.

### 4. 실패 사례 분류

각 실패를 다음 중 하나로 분류한다.

- `PROMPT_CLASSIFICATION`
  - 필수·선호·제외·비선호 강도 분류 오류
- `PROMPT_OMISSION`
  - 사용자가 말한 조건 누락
- `PROMPT_HALLUCINATION`
  - 사용자가 말하지 않은 조건 생성
- `SCHEMA_VALIDATION`
  - Pydantic 스키마 또는 validator 오류
- `PARSER_NORMALIZATION`
  - 과목명, 시간, 배열 등의 후처리 오류
- `TEST_EXPECTATION`
  - 기대값 자체가 의심되지만 임의 수정 금지
- `API_OR_ENVIRONMENT`
  - 타임아웃, 인증, 네트워크, 호출 제한 문제
- `NON_DETERMINISTIC`
  - 동일 입력에서 결과가 불안정하게 달라지는 문제

### 5. 수정 대상 결정

프롬프트 문제로 판단된 경우에만 프롬프트를 수정한다.

프롬프트보다 스키마나 후처리 문제라면
그 사실을 보고하고 해당 코드의 최소 변경만 수행한다.

모든 실패를 프롬프트 문제로 간주해서는 안 된다.

### 6. 프롬프트 수정

프롬프트 변경은 다음 원칙을 지킨다.

- 특정 테스트 문장을 그대로 예시로 추가하지 않는다.
- 테스트 ID나 고유 과목명을 하드코딩하지 않는다.
- 의미가 같은 다양한 표현에 적용 가능한 일반 규칙으로 수정한다.
- 기존 규칙과 충돌하거나 중복되는 규칙을 만들지 않는다.
- 프롬프트를 불필요하게 길게 만들지 않는다.
- 한 번에 여러 원인을 추측해 대규모 수정하지 않는다.
- 조건의 강도를 임의로 강화하거나 약화하지 않는다.

한 번의 스킬 실행에서 프롬프트 수정은 최대 2회까지만 수행한다.

### 7. 전체 회귀 테스트

수정 후 실패한 테스트만 실행하지 말고 전체 평가 테스트를 다시 실행한다.

```bash
pytest -m llm_eval
pytest -m "not llm_eval"
```

기존 통과 테스트가 새로 실패하면 회귀로 기록한다.

회귀가 발생한 수정은 원칙적으로 유지하지 않는다.
더 나은 일반 규칙으로 해결할 수 없으면 변경 전 상태로 되돌리고 보고한다.

## 수정 허용 범위

### 우선 수정 대상

- 자연어 구조화 LLM 프롬프트
- 프롬프트 조립 함수

### 원인 확인 후 최소 수정 가능

- Pydantic 출력 모델 validator
- JSON 파싱 코드
- 과목명 및 시간 정규화 코드
- LLM structured output 설정

### 수정 금지

- 평가 케이스 삭제
- 기대 결과 임의 변경
- 테스트 `skip` 처리
- 테스트 `xfail` 처리
- assertion 완화로 오류 숨기기
- 실패 입력을 프롬프트에 그대로 하드코딩
- API 호출 실패를 성공으로 처리
- 사용자 승인 없는 주요 스키마 필드명 변경
- unrelated 파일의 대규모 리팩터링

## 평가 방식

### 배열 필드

과목명과 교양 영역 배열은 순서가 의미 없으면 집합 기준으로 비교한다.

단, 다음은 반드시 별도로 검사한다.

- 과목이 올바른 필드에 들어갔는가
- 선호 과목이 필수 과목으로 강화되지 않았는가
- 비선호 과목이 제외 과목으로 강화되지 않았는가
- 사용자가 말하지 않은 값이 추가되지 않았는가

### 빈 필드

사용자가 특정 조건을 말하지 않았다면 해당 필드는 빈 배열 또는 `None`이어야 한다.
프로젝트의 실제 기본값 규칙을 따른다.

### 복합 문장

하나의 문장에 여러 조건이 있어도 각 조건을 독립적으로 추출해야 한다.

예:

- 반드시 듣고 싶은 과목
- 가능하면 듣고 싶은 과목
- 절대 제외할 과목
- 가능하면 피할 과목
- 선호 영역
- 시작 가능 시각

### 부정 표현

문장 후반의 부정 또는 완화 표현을 우선 고려한다.

예:

- "꼭 듣고 싶은 것은 아니고 가능하면 넣어줘"
  - 필수가 아니라 선호
- "싫긴 하지만 절대 제외할 정도는 아니야"
  - 제외가 아니라 비선호

## LLM 테스트 안정성 규칙

- 가능한 경우 temperature를 0으로 설정한다.
- 같은 테스트를 통과할 때까지 무제한 반복 호출하지 않는다.
- 일시적 API 오류와 의미 분석 실패를 구분한다.
- API 호출 테스트에는 `llm_eval` 마커를 사용한다.
- 일반 단위 테스트와 실제 API 호출 테스트를 분리한다.
- 실제 LLM 평가 결과에는 입력, 기대값, 실제값, trace ID를 남긴다.
- 동일 케이스의 다회 평가가 필요하면 호출 횟수를 명시적으로 제한한다.

## 결과 보고 형식

작업이 끝나면 다음 형식으로 보고한다.

```text
평가 환경
- 모델:
- temperature:
- 평가 케이스 수:
- 실제 LLM 호출 여부:

변경 전
- 전체 성공:
- 전체 실패:
- 필드별 실패 수:

실패 원인
- PROMPT_CLASSIFICATION:
- PROMPT_OMISSION:
- PROMPT_HALLUCINATION:
- SCHEMA_VALIDATION:
- PARSER_NORMALIZATION:
- API_OR_ENVIRONMENT:
- NON_DETERMINISTIC:

수정 내용
- 수정 파일:
- 변경한 일반 규칙:
- 프롬프트 외 코드 변경 여부:

변경 후
- 전체 성공:
- 전체 실패:
- 기존 테스트 회귀:
- 남은 실패 사례:

판단
- 개선 여부:
- 추가로 사람이 확인할 trace ID:
- 추가 결정이 필요한 사항:
```

프롬프트 변경 전후의 정확도와 회귀 여부가 명확히 드러나야 한다.

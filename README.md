### 1. 프로젝트 소개

#### 1.1. 개발배경 및 필요성
> 편입생의 신분으로써, 부산대에 올해 입학하게 되었는데 과에서 안내가 지연되어 제대로 된 수강신청에 대한 안내를 뒤늦게 접하게 되었다.
> 확인을 하니 편입학의 최종결과가 나오기 이전 이미 희망과목에 대한 사전 수강신청(과목담기) 가 이미 종료된 상태였고, 부산대의 경우에는
> 단과대학교가 매우 많다보니 수강편람을 살펴봐도 과목수가 많아서 인식하는데 있어 어려움이 있었다. 특히 고전읽기와 토론, 인공지능과 컴퓨팅사고와 같은  
> 필수 교양의 경우 그 분반의 수만해도 50개가 넘어가며 시간표도 날짜별 정렬이 불가능하여 일일히 원하는 조건을 수강편람에서 찾아가야 하는 번거로움이 있었다. 
> 수강신청을 완료하고 , 개강을 한후 신입생에게 물어봤을때 대부분이 수강편람에 대한 가독성과 신청방법이 모호하다 보니 안내를 받아도 신청하는데 있어서 어려움 
> 이 많았고 몇몇 학우들은 원하는 과목을 놓쳐버려서 차선의 시간표를 구성하는데 시간과 노력을 많이 들였다고 답변하였다. 이처럼, 현 부산대 수강신청 프로세스에서
> 발견되는 문제점은 1) 방대한 수강과목으로 인한 가독성의 불편 , 2) 수강편람내 정렬기능의 부재로 원하는 정보를 찾아가는데 불편함 , 3) 일부 신/편입생의 경우 사전 시간표제
> 작에서 희망과목 수강담기가 불가능하므로 이상적 시간표의 구성이 어렵다 로 귀결될수 있었다.
> 아래는 24~26년도 부산대학교 편입학 합격자 수를 정리한 표이다. 표에서 볼 수 있듯이 몇백 명의 인원이 편입생의 신분으로 부산대학교에 들어오고, 여기에 추가 합격 신입생의 숫자도 더해지면, 적지 않은 수의 인원이 별다른 수강신청 안내 없이 혼자 수강신청을 진행해야 하는 상황에 놓이는 것이다.

|  연도   |  총 합격자 수  |
| :-----: | :----: |
| 2024학년도  | 336명 |
| 2025학년도 | 275명 |
| 2026학년도 | 203명 |


#### 1.2. 개발 목표 및 주요 내용

프로젝트의 목표 : 부산대 수강신청 도우미 프로그램 (PlaNU) 개발을 통한 수강정정기간 민원 감소 

주요 내용 : 사용자로부터 업로드된 수강편람 및 프롬프트를 기반으로 서버 및 LLM의 활용을 이용한 이상적 시간표 제시

#### 1.3. 세부내용

> PlaNU는 다음 순서로 동작한다.
>
> 1. **사용자**: 전공 수강편람 엑셀 파일을 업로드하고, 원하는 공강일·수업 시간·필수 과목 등의 조건을 문장으로 입력한다.
> 2. **서버**: 업로드된 파일을 읽어 과목명, 분반, 수업 시간, 강의실, 학점 정보를 정리한다.
> 3. **조건 해석 LLM**: 사용자의 문장에서 반드시 지켜야 하는 조건과 가능하면 반영할 선호 조건을 구분한다.
> 4. **검색 도구**: 필요한 경우 실제 수강편람에서 과목과 분반 후보를 찾는다. 후보가 여러 개이면 자동 선택하지 않고 사용자에게 확인을 요청한다.
> 5. **사용자**: 전공 과목과 분반을 직접 확인하고 최종 확정한다.
> 6. **검토 LLM**: 앞 단계에서 찾은 과목명과 조건이 사용자의 뜻에 맞는지 다시 확인한다.
> 7. **서버**: 확정된 전공 과목과 교양 후보를 합쳐 시간표를 만들고, 시간 겹침·강의실 이동 거리·연속 수업·학점 초과 여부를 검사한다.
> 8. **앱**: 검사를 통과한 시간표 중 사용자 조건을 가장 잘 만족하는 상위 결과를 보여준다.
>
> LLM은 사용자의 뜻을 해석하고 서로의 결과를 교차 검토한다. 실제 과목의 존재 여부와 시간표 충돌 여부는 서버 코드가 마지막으로 확인한다.

#### 1.4. 기존 서비스 대비 차별성

> 부산대 수강신청을 직접적으로 연습할수 있는 페이지는 총 2건 웹으로 되어있으나, 이것은 수강신청 자체를 연습하는데 그 목적이 있다.
> 따라서, 사용자가 사전에 시간표를 만들어보거나 수강편람을 익숙하게 다루고 원하는 조건대로 정렬할수 있도록 하는데는 거리가 멀고
> 각각 23년도와 24년도의 수강과목 및 교육과정을 포함하고 있어서 시간적 괴리가 존재하는 한계가 있다.
> PlaNU 의 경우에는, 개발자가 교양과목에 대한 수강편람을 주기적으로 갱신하고 사용자가 직접 최신의 전공 수강편람을 업로드 하는 방식이기 때문에
> 업데이트를 통해 시간적 괴리를 극복할수 있으며 수강편람을 일일히 정렬하거나 조건을 설정하는것 역시도 간편하게 할수 있으므로 사용자의 편리성을 보장한다.
> 또한, 앱을 통한 개발이므로 기존의 PC환경의 웹과는 차별화를 가지고 있으며 최근 증가하는 모바일 사용에 맞춰서 사용자의 간편함을 최대로 추구할수 있다.

#### 1.5. 사회적 가치 도입 계획

> 본 서비스는 학사 시스템에 익숙하지 않은 신입생·편입생의 수강신청 정보 비대칭을 해소한다. 복잡한 제약 조건을 인지하지 못해 발생하는 오신청을 줄임으로써, 개강 직후 정정 기간에 집중되는 민원을 감소시키고 행정 인력 낭비를 절감할 것으로 기대된다. 나아가 유사한 문제를 겪는 타 대학으로 서비스를 확장해 대학 전반의 수강신청 경험을 개선하는 범용 솔루션으로 발전시킬 수 있다.

### 2.상세설계

#### 2.1. 시스템 구성도

PlaNU는 사용자가 올린 전공 수강편람과 자연어 조건을 바탕으로 시간표 후보를 만드는 서비스이다.

> 아래 내용은 현재 개발 방향을 기준으로 정리한 목표 동작이다. 일부 기능은 구현 또는 화면 연결 과정에 있을 수 있다.

전체 시스템은 아래 순서로 동작한다.

1. 사용자가 전공 수강편람 파일을 업로드한다.
2. 사용자가 원하는 수업 조건을 문장으로 입력한다.
3. 서버가 수강편람 내용을 정리하고, 첫 번째 LLM이 사용자의 문장에서 필요한 과목과 조건을 해석한다.
4. 필요한 경우 과목 검색 도구, 분반 조회 도구 등 다른 도구를 사용해 실제 수강편람에서 후보를 찾는다.
5. 사용자가 전공 과목과 분반을 직접 확인하고 확정한다.
6. 두 번째 LLM이 앞에서 찾은 교양 후보와 사용자가 확정한 전공 과목을 다시 확인한다.
7. 서버가 수업 시간 충돌, 연속 수업, 강의실 이동 거리, 학점 초과 여부 등을 검사한다.
8. 문제가 없는 시간표 중 조건을 가장 잘 만족한 결과를 사용자에게 보여준다.

두 개의 LLM은 역할이 다릅니다.

- **조건 해석 LLM**: 사용자의 문장을 읽고 필요한 조건과 과목 후보를 찾는다.
- **검토 LLM**: 과목명이 실제 수강편람과 맞는지, 앞 단계의 판단에 문제가 없는지 다시 확인한다.

최종 결정은 LLM만으로 하지 않는다. 실제 과목의 존재 여부와 시간표 충돌 여부는 서버 코드가 다시 검사한다.

### 3. 개발결과

#### 3.1. 전체 시스템 흐름

PlaNU는 하나의 `session_id`를 사용하여 사용자가 진행한 작업을 단계별로 이어서 관리한다.

```text
전공 수강편람 업로드
        ↓
사용자 조건 입력
        ↓
조건 해석 LLM이 요청 분석
        ↓
실제 수강편람에서 과목·분반 후보 검색
        ↓
사용자가 전공 과목·분반 확정
        ↓
교양 후보와 전공 과목 합치기
        ↓
검토 LLM이 과목명과 후보를 다시 확인
        ↓
서버가 시간표 충돌 검사
        ↓
검증된 시간표 생성
        ↓
점수 계산 및 상위 시간표 제공
```

##### 1단계: 전공 수강편람 업로드

사용자는 부산대학교 수강편람에서 내려받은 전공 수강편람 엑셀 파일을 업로드한다.

서버는 파일을 읽어 다음 정보를 정리한다.

- 과목명
- 과목 코드
- 분반
- 수업 요일과 시간
- 담당 교수
- 강의실
- 학점

파일 형식이 잘못되었거나 필요한 정보가 없으면 다음 단계로 넘어가지 않고 다시 업로드하도록 안내한다.

##### 2단계: 사용자 조건 입력

사용자는 원하는 조건을 문장으로 입력한다.

예시는 다음과 같다.

```text
금요일은 공강으로 만들고 싶어요.
오전 10시 이전 수업은 제외해 주세요.
컴퓨팅 사고 관련 교양은 가능하면 듣고 싶어요.
5시 30분 전에는 모든 수업이 끝났으면 좋겠어요.
```

조건 해석 LLM은 사용자의 문장에서 다음을 구분한다.

- 반드시 지켜야 하는 조건
- 가능하면 반영할 선호 조건
- 필수로 듣고 싶은 과목
- 제외하고 싶은 과목
- 과목을 더 찾아야 하는 요청

##### 3단계: 과목 후보 검색

사용자가 말한 과목명이 실제 수강편람 이름과 다를 수 있다.

예를 들어 사용자는 `컴퓨팅 사고`라고 입력하지만 실제 과목명은 `컴퓨팅사고와인공지능`일 수 있다.

이 경우 PlaNU는 과목명을 바로 확정하지 않고 다음 순서로 처리한다.

1. 사용자의 표현을 원문에 가깝게 보관한다.
2. 공백과 특수문자를 정리한다.
3. 실제 수강편람에서 비슷한 과목을 찾는다.
4. 후보가 하나로 명확하면 바로 사용한다.
5. 후보가 여러 개이면 사용자에게 선택을 요청한다.
6. 후보가 없으면 찾지 못했다고 안내한다.

##### 4단계: 전공 과목 확정

찾아낸 전공 과목과 분반은 사용자가 직접 확인하고 확정한다.

PlaNU는 후보를 보여줄 수 있지만, 비슷한 과목이나 여러 분반 중 하나를 임의로 선택하지 않는다.

사용자가 확정한 전공 과목은 이후 시간표 생성의 고정된 기준이 된다.

##### 5단계: 교양 후보 준비

조건 해석 LLM과 검색 도구가 사용자의 요구에 맞는 교양 과목 후보를 찾는다.

예를 들어 금요일 공강이 반드시 필요하면 금요일 수업이 있는 분반은 후보에서 제외한다. 반대로 “가능하면 수요일도 비우고 싶다”와 같은 선호 조건은 후보를 완전히 제외하지 않고 점수를 계산할 때 우선순위로 사용한다.

##### 6단계: 두 번째 LLM의 교차 검토

과목 이름을 잘못 읽거나 비슷한 과목을 잘못 연결하는 문제를 줄이기 위해, 앞 단계와 다른 역할의 LLM이 결과를 다시 검토한다.

검토하는 내용은 다음과 같다.

- 사용자의 표현과 선택한 과목이 의미상 맞는가
- 검색된 과목이 실제 후보 목록 안에 있는가
- 필수 과목과 선호 과목이 뒤바뀌지 않았는가
- 여러 후보 중 하나를 근거 없이 선택하지 않았는가

두 번째 LLM도 최종 결정을 단독으로 내리지 않는다. 검토 결과는 서버 코드의 마지막 확인을 거칩니다.

##### 7단계: 서버 충돌 검사

사용자가 확정한 전공 과목과 교양 후보를 합쳐 여러 시간표를 만든다.

서버는 각 시간표에 다음 문제가 있는지 확인한다.

- 같은 시간에 두 수업이 겹치는가
- 수업 사이 이동 시간이 부족한가
- 강의실 사이 거리가 너무 먼가
- 연속 수업 조건을 지킬 수 있는가
- 신청 학점이 목표 범위를 넘는가
- 반드시 지켜야 하는 공강·시작 시간·종료 시간 조건을 어기는가

문제가 있는 시간표는 결과에서 제외한다.

##### 8단계: 상위 시간표 제공

충돌이 없는 시간표만 남긴 뒤 사용자 조건을 얼마나 잘 만족하는지 점수를 계산한다.

상위 시간표에는 다음 내용을 함께 보여준다.

- 시간표 순위
- 전체 수업 목록
- 총 학점
- 공강 요일
- 첫 수업 시작 시간
- 마지막 수업 종료 시간
- 반드시 지킨 조건
- 반영된 선호 조건
- 반영하지 못한 조건과 이유

사용자는 결과를 확인한 뒤 조건을 수정하고 다시 추천받을 수 있다.

<br/>

#### 3.2. 기능 설명

##### `1. 전공 수강편람 업로드`

사용자가 자신의 학과 전공 수강편람 엑셀 파일을 올리는 기능이다.

- `.xlsx` 파일을 우선 사용한다.
- 학과와 파일 형식을 확인한다.
- 과목명, 과목 코드, 분반, 시간, 강의실, 학점을 읽는다.
- 파일을 읽지 못하면 오류 이유와 다시 시도하는 방법을 보여준다.
- 업로드가 끝나면 같은 `session_id`를 다음 단계에서도 계속 사용한다.

##### `2. 자연어 조건 입력`

사용자가 원하는 시간표 조건을 문장으로 입력하는 기능이다.

입력 예시:

```text
금요일은 반드시 공강으로 만들어 주세요.
오전 10시 이전 수업은 피하고 싶어요.
컴퓨터프로그래밍은 꼭 듣고 싶어요.
가능하면 수업이 한쪽 요일에 모였으면 좋겠어요.
```

입력된 조건은 다음 두 종류로 나누어 관리한다.

- **필수 조건**: 반드시 지켜야 하는 조건
- **선호 조건**: 가능하면 반영할 조건

필수 조건을 만족하지 못한 시간표는 생성 결과에서 제외한다. 선호 조건은 후보의 순위를 정할 때 사용한다.

##### `3. 과목 검색 및 후보 찾기`

사용자가 입력한 과목명이나 조건에 맞는 과목을 실제 수강편람에서 찾는 기능이다.

- 특정 과목 이름 검색
- 과목 코드 검색
- 교양 영역별 검색
- 요일·시간 조건 검색
- 한 과목의 분반 목록 확인
- 특정 분반의 상세 정보 확인

과목명이 정확하지 않아도 비슷한 후보를 찾을 수 있다. 다만 후보가 여러 개이면 자동으로 첫 번째 과목을 고르지 않고 사용자에게 확인을 요청한다.

##### `4. 전공 과목·분반 확정`

검색된 전공 과목과 분반을 사용자가 직접 선택하는 기능이다.

- 과목별 분반 목록을 확인한다.
- 수업 요일과 시간을 비교한다.
- 교수와 강의실 정보를 확인한다.
- 이미 선택한 과목과 시간이 겹치면 경고한다.
- 사용자가 최종 확인한 선택만 저장한다.

##### `5. 교양 후보 준비`

전공 시간표에 추가할 교양 과목 후보를 준비하는 기능이다.

- 사용자의 필수 조건을 먼저 적용한다.
- 사용자의 선호 조건은 점수 계산에 사용한다.
- 실제 수강편람에 존재하는 과목만 후보로 사용한다.
- 현재 자료로 확인할 수 없는 조건은 따로 안내한다.

현재 수강편람 정보만으로 판단하기 어려운 예시는 다음과 같다.

- 과제가 적은 수업
- 시험이 없는 수업
- 학점을 받기 쉬운 수업
- 교수 평가가 좋은 수업
- 재미있는 수업

이런 내용은 임의로 추측하지 않고 “현재 자료로 확인할 수 없음”으로 표시한다.

##### `6. 두 LLM의 교차 검토`

PlaNU는 서로 다른 역할을 맡은 두 LLM을 사용한다.

###### 조건 해석 LLM

사용자의 문장을 읽고 다음 내용을 정리한다.

- 필수 조건
- 선호 조건
- 필수 과목
- 제외 과목
- 검색이 필요한 과목 표현

###### 검토 LLM

첫 번째 단계에서 찾은 과목과 조건을 다시 살펴봅니다.

- 과목 이름이 사용자의 뜻과 맞는지 확인
- 실제 후보 목록에 없는 과목을 만들지 않았는지 확인
- 여러 후보 중 하나를 근거 없이 선택하지 않았는지 확인
- 조건이 잘못 분류되지 않았는지 확인

두 LLM이 같은 답을 했더라도 서버는 실제 수강편람에 존재하는 과목인지 한 번 더 검사한다.

##### `7. 시간표 생성`

확정된 전공 과목과 교양 후보를 조합하여 여러 시간표를 만드는 기능이다.

시간표를 만들 때 서버가 다음 내용을 확인한다.

- 수업 시간 겹침
- 강의실 이동 거리
- 수업 사이 이동 가능 시간
- 연속 수업 여부
- 총 신청 학점
- 필수 공강 요일
- 가장 빠른 수업 시작 시간
- 가장 늦은 수업 종료 시간
- 필수 과목 포함 여부
- 제외 과목 포함 여부

하나라도 반드시 지켜야 하는 조건을 어긴 시간표는 제외한다.

##### `8. 시간표 검증 및 순위 계산`

충돌이 없는 시간표를 대상으로 점수를 계산한다.

예를 들어 다음 요소를 사용할 수 있다.

- 사용자가 원하는 공강일을 만들었는가
- 아침 수업을 줄였는가
- 수업이 여러 날로 지나치게 흩어지지 않았는가
- 목표 학점에 가까운가
- 강의실 이동이 무리하지 않은가
- 선호 과목을 포함했는가

필수 조건은 통과 여부를 판단하고, 선호 조건은 시간표 사이의 순위를 정하는 데 사용한다.

##### `9. 추천 결과 제공`

점수가 높은 시간표를 사용자에게 순서대로 보여주는 기능이다.

각 결과에는 다음 내용을 표시한다.

- 순위
- 주간 시간표
- 과목과 분반
- 총 학점
- 공강 요일
- 시작·종료 시간
- 조건별 충족 여부
- 추천 이유
- 경고 또는 반영하지 못한 조건

사용자는 결과를 선택하거나 조건을 수정하여 다시 시간표를 만들 수 있다.

##### `10. 오류 안내 및 다시 시도`

문제가 발생했을 때 단순히 실패했다고만 표시하지 않고, 사용자가 다음에 무엇을 해야 하는지 안내한다.

주요 오류 예시는 다음과 같다.

- 수강편람 파일 형식이 잘못됨
- 수강편람에서 필요한 정보를 찾지 못함
- 세션이 만료됨
- 전공 과목이 아직 확정되지 않음
- 과목명이 여러 후보로 나뉨
- 조건을 만족하는 시간표가 없음
- 서버 또는 LLM 연결 실패

오류가 발생해도 가능한 조건은 유지하고, 문제가 된 단계부터 다시 진행할 수 있도록 구성한다.

#### 4.1. PlaNU 백엔드 API 흐름

프론트엔드는 아래 순서로 하나의 `session_id`를 이어서 사용한다. 세션이 만료되어 `SESSION_NOT_FOUND`가 반환되면 전공 수강편람 업로드부터 다시 시작해야 한다.

1. `GET /health`
   - 서버 상태 확인용이다.
   - 성공 응답 예: `{"status":"ok"}`

2. `POST /catalog/major`
   - Content-Type: `multipart/form-data`
   - 필수 필드: `department`, `major_catalog` (`.xlsx`)
   - 다음 단계에서 `session_id`를 재사용한다.
   - 주요 성공 필드: `session_id`, `session_stage="catalog_parsed"`, `parsed_course_count`, `warnings`

3. `POST /major/preview`
   - Content-Type: `application/json`
   - 필수 필드: `session_id`, `prompt`
   - 다음 단계에서 `preview_id`를 재사용한다.
   - `can_confirm=false`이면 `/major/confirm`을 호출하지 말고 사용자가 프롬프트를 수정해야 한다.

4. `POST /major/confirm`
   - Content-Type: `application/json`
   - 필수 필드: `session_id`, `preview_id`
   - 성공 시 세션 단계는 `major_confirmed`이다.

5. `POST /general/prepare`
   - Content-Type: `multipart/form-data`
   - 필수 필드: `session_id`
   - 선택 필드: `elective_area`, `elective_catalog` (`.xlsx`). `elective_area`가 없으면 전체 교양 영역을 사용하고, 파일이 없으면 서버 fallback 교양선택 데이터를 사용한다.
   - 성공 시 세션 단계는 `general_ready`이다.

6. `POST /recommend/generate`
   - Content-Type: `application/json`
   - 필수 필드: `session_id`
   - 선택 필드: `target_total_credits`, `additional_elective_count`, `hard_conditions`, `preference_prompt`, `max_candidates`
   - 프롬프트나 학점 목표가 바뀌면 이 단계부터 다시 호출한다.
   - 성공 시 세션 단계는 `candidates_generated`이고, `unsupported_conditions`, `warnings`, `truncated`, `diagnostics`를 함께 확인한다.

7. `POST /recommend/rank`
   - Content-Type: `application/json`
   - 필수 필드: `session_id`
   - 선택 필드: `template` (`balanced`, `free_day_priority`, `no_morning_priority`, `compact_schedule`), `top_n`
   - 템플릿만 바뀌면 `/recommend/generate`를 다시 호출하지 않고 이 API만 다시 호출한다.
   - 성공 시 세션 단계는 `ranking_completed`이며, `ranked_candidates`의 각 항목은 `rank`, `raw_score`, `score_components`, `load_satisfaction`을 포함한다.

대표 오류 응답 형식:

```json
{
  "error": {
    "code": "INVALID_SESSION_STAGE",
    "message": "전공 확정과 교양 후보 준비가 완료된 세션에서만 시간표를 생성할 수 있습니다.",
    "hint": null,
    "details": {}
  }
}
```

주요 오류 코드: `MAJOR_CATALOG_REQUIRED`, `INVALID_FILE_EXTENSION`, `INVALID_EXCEL_FILE`, `FILE_TOO_LARGE`, `SESSION_NOT_FOUND`, `INVALID_SESSION_STAGE`, `MAJOR_PREVIEW_NOT_CONFIRMABLE`, `INVALID_ELECTIVE_AREA`, `UNKNOWN_RANKING_TEMPLATE`, `INVALID_TOP_N`.

테스트 실행:

```bash
cd C:\hackerton
python -m pytest backend\tests -v
python -m pytest backend\tests\integration -v
python -m pytest backend\tests -m "not llm_live" -v
python -m pytest backend\tests -m llm_live -v
```

실제 LLM 파서 테스트는 비용과 네트워크 상태의 영향을 받으므로 기본 테스트에서 제외된다. 운영 경로와 같은 LLM/proxy를 호출하려면 명시적으로 환경 변수를 설정한 뒤 `live_llm` marker만 실행한다. 인증값은 로그에 출력하지 않으며, trace에는 모델명, proxy 사용 여부, case 이름, latency, 성공/실패 요약만 남깁니다.

```bash

set PROXY_TOKEN=...
set OPENAI_MODEL=openai/gpt-4.1-mini
set CHAT_PROXY_URL=https://mlapi.run/.../v1
python -m pytest backend\tests\live_llm -m live_llm -v -s
```
